# 바둑 100 — 100단계로 배우는 바둑

19×19 정규 바둑판에서 **규칙부터 실전까지** 단계적으로 배우는 학습 게임.
빌드 도구도 외부 라이브러리도 쓰지 않는다. 브라우저에서 바로 돌아가고,
핵심 로직은 전부 `node --test`로 검증된다.

```bash
npm start        # http://localhost:8080 에서 열림
npm test         # 규칙 엔진·문제 엔진·사활·AI·복기 단위 테스트 (87개)
```

브라우저 통합 테스트(선택, `npm i -D playwright` 필요):

```bash
node tools/serve.js 8099 &
node tools/smoke.js        # 모든 화면을 실제로 열어 본다 (28개 검사)
node tools/playthrough.js http://localhost:8099 50   # LEVEL 1~50을 실제로 클릭해 끝까지 깬다
```

## 설계에서 가장 신경 쓴 세 가지

### 1. 정답을 좌표로 하드코딩하지 않는다

문제는 정답 좌표가 아니라 **목표**로 기술하고, 규칙 엔진이 달성 여부를 판정한다.

```js
goal: { type: 'atari', targets: ['D4'] }     // "백 D4를 단수로 만들어라"
```

그래서 같은 목표를 이루는 다른 수가 있으면 **그 수도 정답**이다.
LEVEL 5의 기본 문제는 정답이 두 곳, LEVEL 17의 날일자 문제는 여덟 곳이다.

목표 종류: `capture` `atari` `double-atari` `escape` `connect` `cut` `live` `kill`
`liberties` `ladder` `reduce` `capturable` `ko` `threat` `point`. 상대의 응수도 대본이 아니라 매번 탐색한 결과다.

축처럼 여러 수에 걸친 문제는 세 가지를 함께 쓴다.

| 필드 | 언제 보는가 | 예 |
|---|---|---|
| `moveGoal` | 내 수 직후(응수 전) | "이 수가 상대 활로를 메워 단수를 만들었는가"(축) / "활로를 줄였는가"(먹여치기) |
| `progressGoal` | 상대 응수 뒤 | "축이 아직 성립하는가" / "아직 잡을 수 있는가" |
| `goal` | 언제나 | "돌이 실제로 들려 나갔는가" |

그래서 축을 반대쪽에서 몰면 그 자리에서 **"이쪽으로 몰면 상대가 활로를 늘려
달아납니다"** 라고 되돌려 준다. 정답 수순을 적어 둔 것이 아니라 매번 읽은 결과다.

### 2. 틀렸을 때는 반드시 반면에서 읽어낸 이유를 말한다

"틀렸습니다"로 끝내지 않는다. 활로 수·잡히는 수순·끊기는 자리를 계산해서 설명한다.

> 아직 잡지 못했습니다. 백 돌의 활로가 1개 남아 단수일 뿐입니다.
> 상대는 D3으로 달아납니다.

> 달아나지 못했습니다. 상대가 E16부터 몰면 축으로 잡힙니다.
> 축은 30수쯤 이어지지만 결국 귀에서 잡힙니다.

테스트가 203개 문제 전부에 대해 "오답에 이유가 붙는가"를 검사한다.

### 3. 격언을 절대 법칙으로 가르치지 않는다

모든 공식 카드는 네 칸을 반드시 채운다(요구사항 51).
① 공식 ② 왜 그런가 ③ 언제 유효한가 ④ **언제 예외가 생기는가**

그리고 배운 직후에 반례를 보여 준다(요구사항 74).

- LEVEL 15에서 호구를 배우면, 바로 다음 문제에서 **호구를 이루는 돌이 단수라 호구가 무너지는 국면**을 풀게 한다.
- LEVEL 19의 BOSS는 "한칸뜀에 악수 없다"를 배운 직후 **한칸뜀이 나쁜 국면**이다.

용어도 규칙 / 형태 / 테수지 / 사활 기본형 / 격언 / 전략 원칙으로 구분해 배지로 표시한다(요구사항 73).

## AI 기력을 어떻게 만들었나

낮은 급수를 랜덤 착수로 만들지 않았다(요구사항 57·79).
**사람 초보가 약한 이유는 아무 데나 두어서가 아니라, 방금 둔 곳 주변만 보고 한 수 앞만 읽기 때문이다.**
그래서 급수를 다음 값들로 조절한다.

| 조절 항목 | 18급 | 1급 |
|---|---|---|
| 시야(최근 착수 주변 몇 칸까지 보는가) | 2칸 | 판 전체 |
| 수읽기 깊이 | 1 | 7 |
| 단수 인식률 | 45% | 100% |
| 축 인식률 | 0% | 100% |
| 실수 확률 / 허용 점수차 | 35% / 25점 | 2% / 3점 |

실수는 "그럴듯한 차선을 고르는" 형태로만 넣는다. 점수 차가 큰 수는 실수로도 고르지 않으므로
**눈앞의 따냄이나 유일한 탈출구를 통째로 놓치는 일은 없다.**

검증 결과(9로, 각 판 다른 시드):

- 5급 vs 18급 → 5급 5전 5승
- 10급 vs 10급 → 12판 중 6승 6패 (색에 따른 치우침 없음)
- 반칙수 0회, 자기 눈 메움 0회, 자기 집을 메우지 않고 공배를 다 메운 뒤 패스로 종료
- 19×19 한 판 8.7초 (한 수 약 30ms)

표시되는 급수는 **예상 기력**이며 실제 인간 급수와 같다고 단정하지 않는다(요구사항 58).
화면에도 그렇게 적혀 있다.

`js/content/validate.js`가 콘텐츠를 자동 검사한다.
**정답이 하나도 없는 문제, 시작부터 목표가 달성된 문제, 활로 0으로 배치된 불가능한 반면**을
전부 잡아내며 테스트에 걸려 있다. 실제로 이 검증기가 초안의 잘못된 국면 19개를 찾아냈고,
콘텐츠를 만드는 과정에서 **엔진 자체의 결함 세 개**까지 드러났다.

1. 포획 탐색이 구역을 처음 한 번만 잡아, 달아나는 돌이 그 밖으로 나가면
   둘 곳이 없어져 "잡혔다"고 잘못 판정했다(CHAPTER 4).
2. 착수 직후의 포획 판정에 "잡는 쪽 차례" 함수를 써서, 나에게 두 수를 연속으로 주고 있었다(CHAPTER 4).
3. 깊이·반경을 잘라 읽는 국지 탐색이 **궁도 사활을 틀리게 판정**했다. 삿갓4궁(T자 4궁)을
   "살아 있다"고 답했는데, 정답은 급소 치중으로 죽는 모양이다(CHAPTER 5).

1·2는 고치고 회귀 테스트를 넣었다(`test/analysis.test.js`).
3은 잘라 읽는 방식 자체의 한계이므로 **완전탐색기를 따로 만들었다**(아래).

### 사활은 잘라 읽지 않고 끝까지 읽는다

`js/engine/tsumego.js`는 **완전히 둘러싸인 무리**에 한해 궁도 안쪽만 두는 완전탐색을 한다.
탐색 공간이 궁도 크기(최대 14점)로 제한되므로 끝까지 읽을 수 있고, 결과가 정확하다.
판정 기준은 규칙 그대로 — 두 번 연속 패스로 끝났을 때 무리가 남아 있으면 삶이며, **빅도 삶으로 센다.**
둘러싸이지 않았거나 노드 한도를 넘으면 판정을 포기하고 기존 국지 탐색으로 되돌아간다.

기본형 10가지를 표로 검증한다(`test/tsumego.test.js`). 궁도 모양과 급소 좌표까지 함께 확인한다.

| 모양 | 결과 | 급소 |
|---|---|---|
| 2궁도 | 죽음 | 두 곳 다 |
| 직삼궁 | 죽음 | 한가운데 |
| 직사궁 · 직오궁 | **삶** | — |
| 사각4궁 | 죽음 | 네 곳 다 |
| 삿갓4궁 | 죽음 | 한가운데 |
| 오궁도화 | 죽음 | 한가운데 |
| 변의 곡사궁 | **삶** | — |
| 귀곡사 | 죽음 | — |
| 두 눈 | **삶** | — |

이 표가 있어야 "직사궁은 치중해도 산다"(LEVEL 43의 반례)를 **자신 있게 가르칠 수 있다.**

검증기는 `live`/`kill` 목표인데 무리가 **바깥으로 트여 있는** 국면도 거부한다.
그런 국면은 완전탐색이 물러서고 국지 탐색이 대신 답하는데, 그 답은 틀릴 수 있고
채점 한 번에 수십 초가 걸린다(실제로 한 국면에서 51초가 걸렸다).
사활 문제는 **닫힌 국면으로만** 만든다는 규칙을 검증기가 강제한다.

## 다음 단계

우선순위 순서(요구사항 78)에 따라 1~5·7~10을 먼저 만들었다. 남은 것은 **PRIORITY 6 — LEVEL 51~100 콘텐츠**다.

엔진은 이미 그 내용을 판정할 수 있다.

- 사활은 `tsumego.js` 완전탐색이 정확히 판정한다 → CHAPTER 6·7의 판정 기반이 이미 있다
- 수상전은 활로 계산과 국지 탐색으로 판정 가능 → CHAPTER 7
- 형세판단·계가는 `score.js`가 이미 제공 → CHAPTER 10
- 포석·격언(CHAPTER 8·9)은 유일한 정답이 없는 영역이라, `point` 목표와 비교 문제(어느 쪽이 큰가)로
  구성해야 한다. 나머지 챕터와 판정 방식이 다르다는 점을 미리 적어 둔다.

즉 남은 작업은 대부분 **콘텐츠 작성**이며, 각 LEVEL을 `ch1.js`~`ch5.js`와 같은 형식으로 쓰고
`node tools/check-content.js`로 검증하면 된다.

그 밖에:

- KataGo 중계 서버(`tools/gtp-bridge.js`) 구현 — 어댑터 쪽 규약은 `KataGoAdapter.js`에 정의되어 있다
- 완전탐색기의 패 처리: 동형반복을 금지하는 방식이라 **팻감이 개입하는 사활**(만년패 등)은
  판정이 정확하지 않을 수 있다. 지금 콘텐츠는 그런 모양을 쓰지 않는다
- 빅·귀곡사처럼 규칙 체계에 따라 달라지는 형태의 계가 처리(요구사항 67)
**콘텐츠 국면은 손으로 고르지 않는다.** CHAPTER 4의 장문·촉촉수·환격·먹여치기,
CHAPTER 5의 궁도 모양은 규칙 엔진으로 전수 조사해 "그 수가 아니면 안 되는" 자리만 골라 넣었고,
수순도 채점기로 끝까지 재생해 확인했다(`tools/` 밖의 일회성 스크립트로 수행).
검증기는 여러 수 문제를 **끝까지 풀어 보고** 도중에 막히면 실패로 잡는다.

실제로 CHAPTER 5를 만들며 손으로 놓은 국면이 여러 번 틀렸다. 백 벽에 구멍이 나 있거나,
막아 놓은 줄 알았던 흑돌이 스스로 단수가 되어 상대에게 반격당하는 국면이었다.
전부 채점기가 먼저 잡아냈다.
