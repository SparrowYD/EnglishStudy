# 바둑 100 — 100단계로 배우는 바둑

19×19 정규 바둑판에서 **규칙부터 실전까지** 단계적으로 배우는 학습 게임.
빌드 도구도 외부 라이브러리도 쓰지 않는다. 브라우저에서 바로 돌아가고,
핵심 로직은 전부 `node --test`로 검증된다.

```bash
npm start        # http://localhost:8080 에서 열림
npm test         # 규칙 엔진·문제 엔진·사활·계가·AI·복기·중계 서버 테스트 (103개, 약 10분)
```

브라우저 통합 테스트(선택, `npm i -D playwright` 필요):

```bash
node tools/serve.js 8099 &
node tools/smoke.js        # 모든 화면을 실제로 열어 본다 (35개 검사, 중계 서버 왕복 포함)
node tools/playthrough.js http://localhost:8099 100  # LEVEL 1~100을 실제로 클릭해 끝까지 깬다
```

## 설계에서 가장 신경 쓴 세 가지

### 1. 정답을 좌표로 하드코딩하지 않는다

문제는 정답 좌표가 아니라 **목표**로 기술하고, 규칙 엔진이 달성 여부를 판정한다.

```js
goal: { type: 'atari', targets: ['D4'] }     // "백 D4를 단수로 만들어라"
```

그래서 같은 목표를 이루는 다른 수가 있으면 **그 수도 정답**이다.
LEVEL 5의 기본 문제는 정답이 두 곳, LEVEL 17의 날일자 문제는 여덟 곳이다.

목표 종류: `capture` `atari` `double-atari` `escape` `connect` `cut` `live` `kill`
`liberties` `ladder` `reduce` `capturable` `ko` `threat` `territory` `point`.
상대의 응수도 대본이 아니라 매번 탐색한 결과다.

축처럼 여러 수에 걸친 문제는 세 가지를 함께 쓴다.

| 필드 | 언제 보는가 | 예 |
|---|---|---|
| `moveGoal` | 내 수 직후(응수 전) | "이 수가 상대 활로를 메워 단수를 만들었는가"(축) / "활로를 줄였는가"(먹여치기) |
| `progressGoal` | 상대 응수 뒤 | "축이 아직 성립하는가" / "아직 잡을 수 있는가" |
| `goal` | 언제나 | "돌이 실제로 들려 나갔는가" |

그래서 축을 반대쪽에서 몰면 그 자리에서 **"이쪽으로 몰면 상대가 활로를 늘려
달아납니다"** 라고 되돌려 준다. 정답 수순을 적어 둔 것이 아니라 매번 읽은 결과다.

### 1-1. 셀 수 있는 것은 센다 — 포석도 마찬가지

포석에는 유일한 정답이 없다. 그래서 CHAPTER 8은 두 가지로 나눴다.

**셀 수 있는 것은 `territory` 목표가 실제로 센다.** `score.js`가 "한 색으로만 둘러싸인 빈 점"을
집으로 세므로, 봉쇄가 덜 되어 있으면 자동으로 0집이 된다. 그 계산으로 격언을 숫자로 바꿨다.

| 확인한 것 | 숫자 |
|---|---|
| 9집을 둘러싸는 데 드는 돌 | 귀 **6점** · 변 **9점** · 중앙 **12점** |
| 같은 귀를 막았을 때 | 2선 **8집** · 3선 **12집** · 4선 **16집** |
| 4선 벽만 세우고 아래를 막지 않으면 | **0집** |

"선귀후변중앙"과 "3선은 실리, 4선은 세력"을 격언이 아니라 **세어 본 결과**로 가르친다.

**셀 수 없는 것은 `point` 목표로 여러 개의 좋은 수를 제시하되, 기준을 반드시 적는다.**
`goal.reason`이 없는 `point` 문제는 검증기가 거부한다 — 오답에게 이유를 말할 수 없기 때문이다
(요구사항 79). 이 규칙을 넣자 예전에 만든 32문제가 걸렸고, 전부 기준을 채워 넣었다.

### 2. 틀렸을 때는 반드시 반면에서 읽어낸 이유를 말한다

"틀렸습니다"로 끝내지 않는다. 활로 수·잡히는 수순·끊기는 자리를 계산해서 설명한다.

> 아직 잡지 못했습니다. 백 돌의 활로가 1개 남아 단수일 뿐입니다.
> 상대는 D3으로 달아납니다.

> 달아나지 못했습니다. 상대가 E16부터 몰면 축으로 잡힙니다.
> 축은 30수쯤 이어지지만 결국 귀에서 잡힙니다.

테스트가 413개 문제 전부에 대해 "오답에 이유가 붙는가"를 검사한다.

### 3. 격언을 절대 법칙으로 가르치지 않는다

모든 공식 카드는 네 칸을 반드시 채운다(요구사항 51).
① 공식 ② 왜 그런가 ③ 언제 유효한가 ④ **언제 예외가 생기는가**

그리고 배운 직후에 반례를 보여 준다(요구사항 74).

- LEVEL 15에서 호구를 배우면, 바로 다음 문제에서 **호구를 이루는 돌이 단수라 호구가 무너지는 국면**을 풀게 한다.
- LEVEL 19의 BOSS는 "한칸뜀에 악수 없다"를 배운 직후 **한칸뜀이 나쁜 국면**이다.

용어도 규칙 / 형태 / 테수지 / 사활 기본형 / 격언 / 전략 원칙으로 구분해 배지로 표시한다(요구사항 73).

## AI 기력을 어떻게 만들었나

낮은 급수를 랜덤 착수로 만들지 않았다(요구사항 57·79).
**사람 초보가 약한 이유는 아무 데나 두어서가 아니라, 방금 둔 곳 주변만 보고 한 수 앞만 읽기 때문이다.**
그래서 급수를 다음 값들로 조절한다.

| 조절 항목 | 18급 | 1급 |
|---|---|---|
| 시야(최근 착수 주변 몇 칸까지 보는가) | 2칸 | 판 전체 |
| 수읽기 깊이 | 1 | 7 |
| 단수 인식률 | 45% | 100% |
| 축 인식률 | 0% | 100% |
| 실수 확률 / 허용 점수차 | 35% / 25점 | 2% / 3점 |

실수는 "그럴듯한 차선을 고르는" 형태로만 넣는다. 점수 차가 큰 수는 실수로도 고르지 않으므로
**눈앞의 따냄이나 유일한 탈출구를 통째로 놓치는 일은 없다.**

검증 결과(9로, 각 판 다른 시드):

- 5급 vs 18급 → 5급 5전 5승
- 10급 vs 10급 → 12판 중 6승 6패 (색에 따른 치우침 없음)
- 반칙수 0회, 자기 눈 메움 0회, 자기 집을 메우지 않고 공배를 다 메운 뒤 패스로 종료
- 19×19 한 판 8.7초 (한 수 약 30ms)

표시되는 급수는 **예상 기력**이며 실제 인간 급수와 같다고 단정하지 않는다(요구사항 58).
화면에도 그렇게 적혀 있다.

`js/content/validate.js`가 콘텐츠를 자동 검사한다.
**정답이 하나도 없는 문제, 시작부터 목표가 달성된 문제, 활로 0으로 배치된 불가능한 반면**을
전부 잡아내며 테스트에 걸려 있다. 실제로 이 검증기가 초안의 잘못된 국면 19개를 찾아냈고,
콘텐츠를 만드는 과정에서 **엔진 자체의 결함 세 개**까지 드러났다.

1. 포획 탐색이 구역을 처음 한 번만 잡아, 달아나는 돌이 그 밖으로 나가면
   둘 곳이 없어져 "잡혔다"고 잘못 판정했다(CHAPTER 4).
2. 착수 직후의 포획 판정에 "잡는 쪽 차례" 함수를 써서, 나에게 두 수를 연속으로 주고 있었다(CHAPTER 4).
3. 깊이·반경을 잘라 읽는 국지 탐색이 **궁도 사활을 틀리게 판정**했다. 삿갓4궁(T자 4궁)을
   "살아 있다"고 답했는데, 정답은 급소 치중으로 죽는 모양이다(CHAPTER 5).

1·2는 고치고 회귀 테스트를 넣었다(`test/analysis.test.js`).
3은 잘라 읽는 방식 자체의 한계이므로 **완전탐색기를 따로 만들었다**(아래).

### 사활은 잘라 읽지 않고 끝까지 읽는다

`js/engine/tsumego.js`는 **완전히 둘러싸인 무리**에 한해 궁도 안쪽만 두는 완전탐색을 한다.
탐색 공간이 궁도 크기(최대 14점)로 제한되므로 끝까지 읽을 수 있고, 결과가 정확하다.
판정 기준은 규칙 그대로 — 두 번 연속 패스로 끝났을 때 무리가 남아 있으면 삶이며, **빅도 삶으로 센다.**
둘러싸이지 않았거나 노드 한도를 넘으면 판정을 포기하고 기존 국지 탐색으로 되돌아간다.

기본형 10가지를 표로 검증한다(`test/tsumego.test.js`). 궁도 모양과 급소 좌표까지 함께 확인한다.

| 모양 | 결과 | 급소 |
|---|---|---|
| 2궁도 | 죽음 | 두 곳 다 |
| 직삼궁 | 죽음 | 한가운데 |
| 직사궁 · 직오궁 | **삶** | — |
| 사각4궁 | 죽음 | 네 곳 다 |
| 삿갓4궁 | 죽음 | 한가운데 |
| 오궁도화 | 죽음 | 한가운데 |
| 변의 곡사궁 | **삶** | — |
| 귀곡사 | 죽음 (규칙) | 급소 A2 |
| 두 눈 | **삶** | — |

귀곡사만 "규칙"이라고 적어 두었다. 탐색은 이 모양을 패라고 답하고, 그 위에 규칙을 얹은 것이다(아래).

이 표가 있어야 "직사궁은 치중해도 산다"(LEVEL 43의 반례)를 **자신 있게 가르칠 수 있다.**

**수상전과 빅도 같은 탐색이 판정한다.** 두 무리가 한 주머니 안에 갇혀 있으면
"어느 쪽이 남는가"를 그대로 물으면 되고, 두 번 연속 패스로 끝났을 때 둘 다 남아 있으면 빅이다.
2선 궁도도 마찬가지다 — 엔진에 물어보니 **2선 여섯 점은 죽고 여덟 점은 살았다**(육사팔활).

궁도를 찾을 때는 **빈 점을 먼저 퍼뜨리고, 그다음 궁도 안에 갇힌 상대 돌만 흡수한다.**
바깥 울타리와 이어진 상대 돌은 흡수하지 않는다 — 그 돌은 궁도의 경계이지 궁도의 일부가 아니다.
이 구분이 없으면 젖혀 좁힌 뒤의 국면에서 울타리를 타고 반상 전체로 새어 나가 판정을 포기하게 된다.

### 빅은 집이 아니다 — 한국식 계가

한국·일본식(집 계가)에서 **빅 안의 빈 점은 집으로 세지 않는다.** 서로 손댈 수 없어서 남은 자리이지,
둘러싸서 얻은 집이 아니기 때문이다. 중국식(점 계가)은 반대로 반면의 모든 점을 세므로 그대로 센다.
이 게임은 한국식으로 계가한다.

빅을 찾는 방법은 **무리가 아니라 자리를 보는 것**이다. 눈이 몇 개인지, 무리가 큰지 작은지 어림하지 않고
공배 하나하나에 이렇게 묻는다.

> 흑이 여기를 메우면 흑이 잡히는가?  백이 메우면 백이 잡히는가?
> **양쪽 다 그렇다면** 아무도 메울 수 없는 자리 — 빅의 공배다.

"빅은 서로 손댈 수 없는 모양"이라는 설명을 그대로 코드로 옮긴 것이다. 이 정의라서 대국 중간의
넓은 빈 곳은 (메워도 안 잡히므로) 저절로 걸러지고, 그냥 죽은 돌도 (메우면 잡히므로) 빅이 되지 않는다.
처음에는 "눈이 둘 미만인데 상대와 공배를 나눠 쓰면 빅"이라는 어림으로 짰다가,
대국 중간의 형세 판단에서 **가운데를 함께 바라보는 모든 벽이 빅으로 잡히는** 것을 보고 버렸다.

```
X X X X X X      C1이 아무도 메울 수 없는 자리다.
O O O O . X      흑이 메우면 흑 D1이 잡히고, 백이 메우면 백 무리가 잡힌다.
. O . X . X      그래서 백의 눈 A1은 집이 되지 않는다 — 한국식 0집, 중국식 1점.
```

반면에는 **빈 네모**로 표시해 집(꽉 찬 네모)과 구분하고, 계가 화면이 왜 빠졌는지 문장으로 말해 준다.

### 패를 삶이나 죽음으로 뭉개지 않는다

예전에는 동형반복 금지(수퍼코) 하나로 사활을 읽었다. 그러면 **되따낼 수 없는 쪽이 그냥 진다.**
게다가 규칙 엔진은 바로 되따내는 수를 애초에 만들어 주지도 않으므로, 패는 조용히 삶이나 죽음으로
뭉개진다. 아래 모양이 그 예다 — 예전 엔진은 이것을 **"백이 산다"**고 단정했다.

```
19  .  .  .  O  X
18  .  O  .  O  X
17  .  O  O  O  X
16  X  X  X  X  X
```

실제로는 흑 B19의 치중부터 **패**다. 백은 팻감 싸움에 이겨야 산다.

그래서 지금은 같은 국면을 두 번 읽는다.

| 가정 | 읽는 방법 |
|---|---|
| ① 잡는 쪽이 패를 이긴다 | 잡는 쪽만 되따내기 금지를 정해진 횟수만큼 어길 수 있다 |
| ② 사는 쪽이 패를 이긴다 | 사는 쪽만 어길 수 있다 |

두 답이 같으면 패와 무관한 확정된 삶/죽음이고, 갈리면 **'패'**다.
어기는 횟수(=팻감)는 유한하므로 탐색은 반드시 끝난다.
잡는 쪽이 패를 못 써서 물러선 적이 한 번도 없으면 ②는 ①과 같은 나무이므로 아예 건너뛴다.

값은 치렀다. 사활 문제 126개를 전수 채점하는 데 108초에서 **301초**로 늘었다.
반면에 기억해 둔 결과를 꺼내 쓰는 열쇠에 **패 자리**를 넣어야 했기 때문이다 —
반면이 같아도 "지금 되따낼 수 없는 자리"가 다르면 다른 국면인데, 예전에는 그것을 섞어 쓰고 있었다.
채점 한 번(수 하나)에 드는 시간은 여전히 수십 밀리초라 화면에서는 차이를 느낄 수 없고,
느려진 것은 **콘텐츠 전수 검증**뿐이다. 정확도를 택했다.

판정 결과가 세 가지가 되었으므로 문제 채점도 셋을 구분한다.
`live` 목표는 패를 삶으로 쳐 주지 않고 **"패가 남습니다 — 아직 산 것이 아닙니다"** 라고 말하고,
`kill` 목표는 **"패로 몰았을 뿐, 아직 잡은 것이 아닙니다"** 라고 말한다.
패로 버티는 것이 정답인 문제는 `goal.allowKo`로 따로 인정한다.

### 귀곡사는 탐색이 아니라 규칙이 정한다

완전탐색기에 귀곡사를 물어보면 **'패'**라고 답한다. 그리고 그게 맞다 — 사는 쪽이 패를 이겨야 산다.
그런데 이 패는 잡는 쪽이 **아무 때나 시작할 수 있다.** 그래서 잡는 쪽은 반면의 팻감을 전부 없앤
뒤에 패를 걸 수 있고, 사는 쪽에게는 이길 방법이 없다. 한국·일본 규칙은 이 사정을 규정으로 못 박았다
— **귀곡사는 죽은 것으로 한다.**

그래서 이 한 모양에만 규칙을 명시적으로 적용한다(`isCornerBentFour`). 다른 패를 임의로 삶이나
죽음으로 바꾸지는 않는다. `rules: 'superko'`로 부르면 규칙을 끄고 탐색 결과(패)를 그대로 볼 수 있고,
테스트가 두 경우를 모두 확인한다.

검증기는 `live`/`kill` 목표인데 무리가 **바깥으로 트여 있는** 국면도 거부한다.
그런 국면은 완전탐색이 물러서고 국지 탐색이 대신 답하는데, 그 답은 틀릴 수 있고
채점 한 번에 수십 초가 걸린다(실제로 한 국면에서 51초가 걸렸다).
사활 문제는 **닫힌 국면으로만** 만든다는 규칙을 검증기가 강제한다.

## 다음 단계

요구사항 78의 우선순위 1~10을 모두 만들었다. **LEVEL 100까지 전부 구현되어 있다.**

남은 것은 기능 확장과 정확도 개선이며, 지금 아는 한계를 그대로 적어 둔다.

- **KataGo 자체는 이 저장소에 없다.** 중계 서버는 GTP를 하는 아무 엔진이나 붙일 수 있게 만들었고,
  KataGo 실행 파일과 모델은 각자 준비해야 한다. 연결에 실패하면 그 이유를 화면에 그대로 보여 준 뒤
  내장 AI로 대체한다
- **내장 GTP 엔진(`tools/gtp-engine.js`)이 내놓는 `winrate`는 진짜 승률이 아니다.** 자체 평가 점수를
  정규화한 상대적 선호도다. 중계 서버의 `status` 응답이 `winrateIsProbability`로 이를 구분해 준다
- **팻감의 크기·개수는 모형이다.** 완전탐색기는 "몇 번 되따낼 수 있는가"로만 패를 근사한다.
  실제 팻감은 반면 전체가 정하는 것이라 궁도만 보고는 알 수 없다. 다만 모르는 쪽으로 뭉개지 않고
  '패'라고 답한다(아래)
- **CHAPTER 8·9의 일부 문제는 `point` 목표**를 쓴다. 포석과 격언에는 유일한 정답이 없기 때문이다.
  대신 기준(`goal.reason`)을 반드시 적었고, 검증기가 그것을 강제한다
- **LEVEL 99의 실전 대국은 별 계산에 넣지 않는다.** 한 판을 이겨야만 커리큘럼이 열리면 진도가
  막히기 때문이다. 결과는 프로필에 남고 화면에 표시된다
- **빅 판정은 국지 탐색에 기댄다.** "서로 메울 수 없는 자리"인지를 한 수 두어 보고 잡히는지로 보는데,
  아주 복잡한 빅(삼패·순환패가 얽힌 형태)까지 맞다고 보장하지는 않는다.
  계가 화면에서 사람이 직접 뒤집을 수 있게 해 둔 것이 최종 안전장치다

### KataGo 연결하기

```bash
# 1) KataGo가 있는 경우
node tools/gtp-bridge.js --katago /경로/katago --model /경로/model.bin.gz --config /경로/gtp.cfg

# 2) KataGo가 없어도 중계 경로 자체는 확인할 수 있다 — 내장 AI를 GTP로 말하게 한다
node tools/gtp-bridge.js --engine node tools/gtp-engine.js
```

띄운 뒤 **설정 → KataGo 연결**에 주소(`http://localhost:8181`)를 넣고 **연결 확인**을 누른다.
안 되면 안 되는 이유가 그대로 뜬다.

기력 조절은 요구사항 60대로 **탐색량**으로만 한다. 어댑터가 급수를 탐색량으로 바꿔 보내고,
중계 서버가 KataGo에는 `kata-set-param maxVisits`로, 급수로 조절하는 엔진에는 역산한 급수로 전달한다.
덤 조절은 여기에 섞지 않는다.

`test/bridge.test.js`가 이 경로를 **실제로 왕복시킨다** — 브라우저가 쓰는 `KataGoAdapter`를 그대로 써서
HTTP → 중계 서버 → GTP 프로세스까지 통과시키고, 접바둑 동기화와 "엔진이 없을 때의 실패 메시지"까지 확인한다.
CHAPTER 6의 국면은 아예 **생성**했다. 궁도 좌표만 주면 백 벽과 흑 벽을 만들어 주는 도구를 쓰고,
완전탐색으로 삶/죽음과 급소를 확인한 것만 넣었다. 손으로 벽을 놓다가 구멍이 나는 실수가
아예 생기지 않는다. 크기 2~6의 **모든** 궁도 모양(폴리오미노)을 전수 조사해
표준 정석과 일치하는 것도 확인했다 — 죽는 모양은 2궁도·삼궁 2종·사각4궁·삿갓4궁·
오궁도화·십자오궁·매화육궁뿐이고 나머지는 전부 산다.

**콘텐츠 국면은 손으로 고르지 않는다.** CHAPTER 4의 장문·촉촉수·환격·먹여치기,
CHAPTER 5의 궁도 모양은 규칙 엔진으로 전수 조사해 "그 수가 아니면 안 되는" 자리만 골라 넣었고,
수순도 채점기로 끝까지 재생해 확인했다(`tools/` 밖의 일회성 스크립트로 수행).
검증기는 여러 수 문제를 **끝까지 풀어 보고** 도중에 막히면 실패로 잡는다.

실제로 CHAPTER 5를 만들며 손으로 놓은 국면이 여러 번 틀렸다. 백 벽에 구멍이 나 있거나,
막아 놓은 줄 알았던 흑돌이 스스로 단수가 되어 상대에게 반격당하는 국면이었다.
전부 채점기가 먼저 잡아냈다.
